# Live Mode Go-Live Checklist

Короткий прикладной чеклист перед переключением системы с `Emulation` на `Live`.
Все пункты обязательны, если иное не отмечено.

## 0. Предусловия окружения

- [ ] На проде крутится последняя сборка из ветки `claude/add-project-documentation-KNaWL`
  (или её merge в main) — т.к. именно там исправлены критичные баги подписи
  MEXC, маппинг `side`/`type` и защита от «призрачных» позиций.
- [ ] Rust toolchain ≥ 1.84, `cargo build --release` проходит без ошибок.
- [ ] Angular frontend собран (`npm run build` в `frontend/`) и раздаётся статикой,
  либо запущен `npm start` для локального UI.
- [ ] Порт `3001` открыт только внутри периметра (через nginx/VPN). Наружу —
  только фронтенд.

## 1. Ключи MEXC и баланс

- [ ] В `.env` заполнены **настоящие** `MEXC_API_KEY` / `MEXC_API_SECRET`
  (не placeholder, длина ≥ 16 символов). Проверка усилена в
  `src/main.rs` — заглушки (`your_…`, `placeholder`, `changeme`, `<…>`)
  отбрасываются автоматически.
- [ ] Ключ выпущен под фьючерсный аккаунт MEXC с правами **Read + Trade**,
  но **без Withdraw**.
- [ ] Whitelist IP на стороне MEXC включает IP прод-сервера.
- [ ] При старте в логах видны строки:
    - `✅ MEXC API keys validated | USDT free: … | locked: …`
    - `💰 Capital synced from MEXC balance: $… (was $… in config)`
    - `✅ MEXC API client connected to all symbols (Live trading ready)`
- [ ] Фьючерсный кошелёк MEXC содержит USDT в количестве, достаточном для
  `position_size_percent × leverage` по 3 символам (BTC/ETH/SOL). Рекомендуется
  минимум `$100` для стартового теста.

## 2. Конфигурация торговли

- [ ] `config.toml` → `[trading]` проверен:
  - `leverage` ≤ реально разрешённого на инструменте
  - `position_size_percent` не более `10.0` для первого запуска
  - `max_positions` = 2 (по 1 на направление)
- [ ] `TradingSettings` в `.kiro/system_state.json` согласованы с UI-формой.
- [ ] `[monitoring].stale_timeout_ms` ≤ 300 — лаги больше порога останавливают
  торговлю автоматически.

## 3. Предстартовые функциональные тесты (в Emulation)

Перед включением Live прогоните все сценарии в режиме `Emulation`:

- [ ] WS-стримы Binance и MEXC подключились по всем 3 символам
  (`binance-btc`, `mexc-btc`, …). `GET /health/detailed` → все компоненты
  `Healthy`.
- [ ] Открытие позиции: сигнал → `🚀 OPENED (EMULATION)` в логах, появляется в
  `positions` в UI.
- [ ] Закрытие по timeout: через `quick_exit_timeout` позиция уходит в
  `💰 CLOSED`, PnL и Fee начислены в `capital`.
- [ ] Take-profit и stop-loss срабатывают (проверьте вручную в логах).
- [ ] Смена настроек через UI (`Trading Settings → Apply`) отражается в
  логе `⚙️ Settings updated` и в `.kiro/system_state.json`.
- [ ] `Старт / Стоп` из UI меняет `is_running` во всех `PositionManager`.
- [ ] `Переключить режим` блокируется, пока торговля запущена (см.
  `system_manager_optimized::switch_mode`).

## 4. Frontend safety

- [ ] При отключении backend в UI появляется жёлтый баннер
  «Нет соединения с сервером — управление торговлей заблокировано».
  Кнопки `Запустить / Переключить режим` становятся неактивными.
  (реализовано в `control-panel.component.ts`).
- [ ] При переподключении баннер исчезает в течение ≤ 2 с.
- [ ] Диалог «Переключение в Live режим» требует явного подтверждения
  перед отправкой `switchMode` на сервер.

## 5. Проверка Live-цепочки на минимальном объёме

Ставим `position_size_percent = 1.0`, `leverage = 5` и проводим один
боевой цикл:

- [ ] Переключаем режим `Emulation → Live` (торговля остановлена).
- [ ] Нажимаем «Запустить».
- [ ] После первого сигнала в логах появляется:
    - `🚀 OPENING (LIVE) | …`
    - `✅ Live order executed on MEXC: <orderId>`
  (если вместо этого видим `❌ Live order rejected by MEXC …` — ордер
  отклонён, **позиция локально не создаётся**; смотрим код ошибки MEXC).
- [ ] На стороне MEXC UI/API вручную подтверждаем открытую позицию с
  тем же `symbol/side/vol`, что и в локальном логе.
- [ ] Закрытие: в логах должно быть
    - `💰 CLOSED | …`
    - `✅ Live close executed on MEXC: <orderId>`
  Если закрытие не удалось — в логе останется `❌ Failed to execute live
  close …`, и позиция **не будет удалена** из локального трекера,
  а будет ретраиться на следующем тике.
- [ ] Баланс USDT на MEXC уменьшился/увеличился согласно PnL + 2× taker fee.

## 6. Наблюдаемость

- [ ] Все события `🚀 OPENING (LIVE)` и `💰 CLOSED` собираются в лог-агрегатор
  (или как минимум пишутся в `logs/`).
- [ ] `.kiro/live.db` растёт при каждом закрытии сделки.
- [ ] `/health` возвращает `OK`, `/health/detailed` — полный JSON.
- [ ] Метрики латентности (`market_state_metrics`, `position_update_metrics`)
  проверены в логах — p95 < 50 мс.

## 7. Аварийные процедуры

- [ ] Документирован аварийный kill-switch:
    1. UI → «Остановить» (через WS-команду `stopTrading`).
    2. Если UI недоступен: `kill -INT $(pgrep arbitrage-system)`.
    3. Принудительное закрытие всех позиций вручную на MEXC UI, если
       сервис не отвечает.
- [ ] Есть чек-скрипт или процедура для сверки локального трекера
  позиций с открытыми позициями на MEXC (см. TODO #7 в аудите —
  автоматическая reconcile-процедура на старте ещё не реализована,
  поэтому перед каждым рестартом сверяемся глазами).

## 8. Известные ограничения (оставлены на следующую итерацию)

- Автоматическая сверка open-позиций с MEXC при старте (reconcile) —
  ещё не реализована. Пока рестарт в Live допускается только при
  отсутствии открытых позиций.
- Конвертация `quantity` в целое число контрактов MEXC — выполняется
  тривиально (через `Decimal`), без подтягивания `contract_size` по
  инструменту. Для мелких сумм это работает, но под каждый символ
  стоит подтянуть шаг из `GET /api/v1/contract/detail`.
- Глобальной FIFO-очереди ордеров между тремя символами нет — защита
  только через per-client 20 req/s rate-limiter. При одновременном
  сигнале по 3 символам отставание отдельных ордеров возможно.
